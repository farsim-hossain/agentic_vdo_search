That changes the design significantly, but it is still workable. Treat Groq VLM as a **rate-limited visual analyst**, not as the main video-processing loop.

## Best Architecture

```text
Video
  -> Local preprocessing (PySceneDetect + OpenCV)
  -> Shot detection & Keyframe deduplication
  -> Storyboard Contact Sheet (timestamp labels burned in)
  -> Local CPU Vector Indexer:
        1. CLIP Image Embeddings (clip-vit-base-patch32)
        2. YOLO nano Object Tags
        3. Frame Hashes
  -> Priority Queue (60s rate limit cooldown)
  -> Groq VLM (qwen/qwen3.6-27b base64 payload, JSON mode)
  -> Text Embedding of VLM Observations (all-MiniLM-L6-v2)
  -> Persistent SQLite Vector Cache (video_index.db)
  -> Local/Groq Text retrieval and timestamped Q&A summary
```

### Local Processing & Frame Embeddings

Run these operations locally on CPU without Groq:

- Shot-boundary detection (`scenedetect`)
- Motion and scene-change scoring
- Keyframe extraction
- CLIP frame vector embeddings (`openai/clip-vit-base-patch32`) for visual vector search
- Object detection (`ultralytics` YOLO nano CPU)
- Frame similarity / perceptual hashing
- Timestamp management

For every shot, create a small storyboard containing 4 to 9 representative frames. Burn the timestamp directly onto each frame:

```text
[00:02:10] [00:02:16] [00:02:23] [00:02:29]
```

Then base64 encode the storyboard (`data:image/jpeg;base64,{...}`) and send it as one VLM request to `qwen/qwen3.6-27b`.

## Vector Search + Groq VLM Workflow

1. User asks a question (e.g. "When does the dog appear?").
2. Query is converted into a CLIP text vector and matched against all keyframe visual vectors in SQLite using cosine similarity.
3. If the top candidate shot has already been analyzed by Groq VLM, return the answer instantly (< 1s).
4. If not yet analyzed by Groq VLM, submit that specific high-ranking shot's storyboard to Groq VLM, wait for response (enforcing the 60s cooldown), embed the text output, update cache, and return grounded answer with timestamps.
